# Architecture Review
Generated: 2026-09-04T21:36:27.403Z
Score: 74/100

## Summary
The codebase has a clean, conventional layered structure (components/hooks/lib/pages) with good use of a Result<T> pattern for storage mutations and reusable pre-built UI primitives. The main structural risks are a stale `contract.ts` whose type signatures no longer match any real implementation, several duplicated cross-cutting concerns (haptic-feedback wrapping, category-list constants) that were re-implemented slightly differently in multiple files, and inconsistent data-loading patterns (hook-based vs. direct storage calls/side-effects during render).

## Issues
### Critical
- [dead_code] src/lib/contract.ts declares itself as the authoritative, 'do not modify' cross-packet interface contract that other files may assume verbatim, but nearly every real implementation has diverged from it: `Fortune`/`FortuneType`/`Category`/`Alert`/`ValidationError` have no relationship to the actual `FortuneRecord`/`AlertItem`/`CategoryId` types in types.ts; `getStatsFn`, `computeFortuneFn`, `useAppDataFn`, `useContentNoticeFn`, `saveFortuneFn`, `loadFortuneFn`, `getAllFortunesFn`, and `formatDateFn` all have parameter/return shapes that don't match the real `getStats`, `computeFortune`, `useAppData`, `useContentNotice`, `saveFortune`, `getFortune`, `listDayLogs`, and `formatDate`. This makes the 'contract' actively misleading rather than authoritative. — Files: src/lib/contract.ts, src/lib/types.ts, src/lib/stats.ts, src/lib/computeFortune.ts, src/hooks/useAppData.ts, src/hooks/useContentNotice.ts, src/lib/date.ts / Fix: Either regenerate contract.ts to match the real, shipped signatures, or delete it and rely on the actual exported types/signatures as the single source of truth. Do not leave a stale contract file that future agents/devs might trust over the real code.

### Warnings
- [duplication] The 'call generateHapticFeedback, swallow throw/rejection outside WebView' pattern is re-implemented with slightly different shapes in at least six places: BottomCTA.tsx's fireHaptic, FloatingTabBar.tsx's inline handler, History.tsx's safeHaptic, Result.tsx's (identical) safeHaptic, Settings.tsx's fireHaptic, and useContentNotice.ts's inline try/catch. Some wrap with `Promise.resolve(...).catch()`, others only try/catch the synchronous throw and leave the returned promise unhandled — an inconsistency that risks unhandled promise rejections in the latter group. — Files: src/components/BottomCTA.tsx, src/components/FloatingTabBar.tsx, src/pages/History.tsx, src/pages/Result.tsx, src/pages/Settings.tsx, src/hooks/useContentNotice.ts / Fix: Extract a single `src/lib/haptics.ts` with one `fireHaptic(type)` helper that always wraps both the synchronous throw and the returned promise, and import it everywhere instead of re-implementing.
- [duplication] The 8-item category id list is hardcoded identically as `ALL_CATEGORIES` in both fortuneEngine.ts and stats.ts, while Input.tsx derives the equivalent list dynamically via `Object.keys(CATEGORY_LABEL) as CategoryId[]`. Three different approaches to the same list of category ids increases the risk that adding/removing a category later only gets applied in some places. — Files: src/lib/fortuneEngine.ts, src/lib/stats.ts, src/pages/Input.tsx, src/lib/types.ts / Fix: Export a single `ALL_CATEGORY_IDS = Object.keys(CATEGORY_LABEL) as CategoryId[]` from lib/types.ts and import it everywhere a full category list is needed.
- [dead_code] `getCharacterImage` and `getFortuneMessage` in fortuneTable.ts (typed against contract.ts's `getCharacterImageFn`/`getFortuneMessageFn`) don't appear to be imported by any page — Home/Result/Share/History all read `TYPE_TABLE` directly instead. They also depend on a `CONTRACT_BAND`/rich-ruin-neutral model that doesn't match the 12-type system actually used elsewhere. — Files: src/lib/fortuneTable.ts, src/lib/contract.ts / Fix: Remove these two exports (and their contract.ts Fn types) if truly unused, or wire them into the pages that need image/message lookups if they were meant to replace direct TYPE_TABLE access.
- [consistency] Data access is inconsistent across pages: Home and Settings load data through the `useAppData` hook (effect-driven, sets `loading` state), whereas History and Share call storage getters (`listDayLogs`, `getFortune`) directly in the component render body, and Result goes further by calling `computeFortune(date)` directly during render — which internally performs a storage *write* (`saveFortune`) as a side effect of rendering. This can double-fire under React.StrictMode/concurrent rendering and mixes read/write concerns into render in a way the rest of the app avoids. — Files: src/pages/Result.tsx, src/pages/Share.tsx, src/pages/History.tsx, src/hooks/useAppData.ts / Fix: Standardize on one data-loading approach — e.g. move `computeFortune`/`getFortune`/`listDayLogs` calls into a `useEffect` or a small `useX` hook per page (mirroring `useAppData`) so storage reads/writes never happen inline during render.

- [structure] src/__scratch__/ScratchApp.tsx is a leftover debugging scratch file whose own header comment says it's safe to delete and untracked, but it still lives inside src/ where it could confuse folder-structure expectations. — Files: src/__scratch__/ScratchApp.tsx / Fix: Delete the file (or the whole __scratch__ directory) now that it's served its purpose, rather than leaving dead placeholder code in the source tree.
- [duplication] Amount.tsx and CountUp.tsx duplicate the same wrapper markup and inline style object (`display:inline-block; whiteSpace:nowrap; fontVariantNumeric:tabular-nums`) plus the `Paragraph.Text` + `formatNumber` + unit composition, differing only in whether the number animates. — Files: src/components/Amount.tsx, src/components/CountUp.tsx / Fix: Extract a shared `NumberDisplay` presentational wrapper (span + style + Paragraph.Text) that both Amount and CountUp compose, so the nowrap/tabular-nums contract lives in one place.

This dual type/value binding is confusing to read and the runtime const doesn't appear to be imported/used anywhere as a value. — Files: src/lib/types.ts / Fix: Drop the runtime const if it's unused, or rename it (e.g. `RouteStateMarker`) to avoid shadowing the type name if it is genuinely needed for typeof-based consumers.
- [structure] `src/pages/__TdsGallery.tsx` sits inside `src/pages/` alongside the app's real routed screens even though it is explicitly dev-only and excluded from production routing/builds, making `pages/` no longer a 1:1 mirror of the app's route table. — Files: src/pages/__TdsGallery.tsx, src/App.tsx / Fix: Move dev-only reference pages to a separate folder such as `src/dev/` to keep `pages/` limited to files that correspond to real, always-registered routes.
